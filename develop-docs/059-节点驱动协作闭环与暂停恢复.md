# 059 — 节点驱动协作闭环与暂停恢复

## 1. 文档地位与实施基线

本设计记录 2026-09-12 用户确认的下一轮实现，配套 [059 实施原稿](./059-implement-节点驱动协作闭环与暂停恢复.md)。050–052 中的数据节点、共享图、作用范围和多 Host 目标继续适用；执行会话、暂停和实施边界按本文修订。

053–058 已实现动态 Claim 核查、共享后端、多 Host 工作租约、用户与资产、核查客户端和边界精简。本轮编码前基线是单 Claim、单 operation 的核查子链。059 已在该基线上实现 parse/split、多个新闻事实的并行推进与下述暂停协议；实际协议见[059 接口文档](./059-接口文档.md)，完成与验证记录见配套实施原稿。历史计划中的全部管理 UI、SSE 等接口不因此视为已完成。

保留当前旧 Mapper 的已有未提交改动。本轮不恢复旧 AgentLoop、整图客户端 lease 或持久化 Timeline，也不新增调度器服务、任务队列、通用 Runtime 抽象或第三方依赖。

## 2. 数据节点与处理规则

Graph 的 Node 表示可保存、引用的数据；Agent、router、worker、merge 是执行角色，不为每个 Agent 创建一个数据节点。

| 输入节点 | operation | 合法后继 | 完成依据 |
|---|---|---|---|
| Source | parse | News 及来源关系 | 匹配输入版本与配置的接受收据 |
| News | split | 零条或多条 Claim 及归属/派生关系 | 接受收据；零条结果同样明确完成 |
| Claim | verify | Verification 及核查关系 | 当前有效结论及接受收据 |

工作从业务事实派生：在请求范围内找缺少有效后继的节点，再生成对应 operation。不能用模型停止、当前没有可领取项、图上存在一个任意下游节点或最深可见节点判定完成。

## 3. Run 的范围、目标与多 operation

- 一图仍只有一个活跃 Run；该 Run 接受 `scope.nodeIds` 和 `until: news | claims | verified`，包含 `operations[]`，不再绑定唯一 target Claim。
- scope 是本次用户选择的数据节点集合。范围在 Run 生命周期中保持明确；不得处理完第一项后退化成扫描整图。有效后继沿本次处理规则扩展范围；普通关系环、共享 Claim 的其他来源不反向扩大范围。
- until 是业务完成边界：达到 News 后停止解析链，达到 Claim 后停止拆分链，达到 verified 后完成范围内需要核查的事实。已有更深数据不因较浅目标被删除。
- 不同 Source、News、Claim 的独立 operation 可以同时 ready，由不同 Host 领取；一个 operation 等待 Review 不阻塞其他独立 operation。
- 每个 verify operation 内保留当前 router、多个核查角度、merge 的工作分解和并行能力。节点间并行和节点内部角度并行是两层业务工作，不新增第二套 Agent 运行时。
- 重叠 scope 节点和共享后继必须归并同一输入版本的处理义务，不因多个路径重复创建 operation。具体字段以本轮 `contracts/*` 为准；业务身份必须稳定绑定节点、阶段、输入版本及配置，不使用数组下标充当身份。

Run 状态从 operation 汇总：仍有可执行项时继续 running；未完成项全部等待人工时才汇总为 waiting；完成必须满足第 5 节闭包条件。failed/cancelled 是终态，不能用 resume 复活。

### 3.1 本轮合同收敛

`GraphRunConfiguration` 保留现有顶层 verify 配置字段；这些字段仍负责核查配置，不是旧协议兼容。新增可选 parse profile 与 `split: { router, merger, agents }`。运行范围实际需要某阶段而配置缺失时明确报错；仅核查现有 Claim 不必配置 parse/split。

parse 提案使用 `news[]`，允许零条或多条新闻。split 继续走 router/workers/merge：各 split-report 保存 `claims[]`，split-merge 用 `selected: [{ reportId, index }]` 引用已保存候选，不让合并模型重新编造另一份候选正文。空 selected 仍须形成明确完成记录。

GraphOperation 保存实际 inputRefs、outputRefs、配置指纹和业务草稿。复用已有阶段产物时同时验证输入、配置和输出版本；人工改动或缺失输出不能沿用旧完成收据。字段细节以本轮正式合同为准。

## 4. 状态所有权与最小实现位置

| 位置 | 保存或执行的职责 |
|---|---|
| Mongo Graph/Run | Node、Edge、输入引用、配置快照、operations、Review、已接受报告、收据与暂停控制 |
| 现有 Graph/Run 业务代码 | 确定需要哪些 operation、校验提案、原子接受产物、推导后继及完成条件 |
| 现有 work/Host 循环 | 发现可执行工作、领取/续租/失效/释放、执行 DSH |
| DSH | 当前领取工作的 Agent 推理、工具、子 Agent、会话和事件 |
| 客户端 | 选择 scope/until，发业务命令，展示各节点与 operation，回答 Review |

沿现有 `backend/run.ts`、`work.ts`、`graph.ts`、`store.ts`、`host.ts` 实现职责，不新增独立 scheduler、ready 队列或通用工作流引擎。API/Host/Mongo 可在同一台机器，单 Host 可以顺序完成全部工作；多 Host 是并行能力，不是最低部署条件。

## 5. 原子提交、版本与不重不漏

1. 输入引用记录实际依赖节点的 revision，配置在 Run 开始时冻结。产物和收据必须能证明对应输入/配置，旧结果不能仅因节点仍存在就算当前完成。
2. 同一逻辑工作使用稳定提案/收据身份；相同输入的请求重放返回已接受结果，不同输入复用身份明确冲突。模型或外部工具可能重复执行，业务结果只接受一次。
3. 接受结果、关系、空结果完成收据和 operation 推进在同一次 Mongo CAS 中成立。新后继工作由接受后的业务状态确定性派生，不依赖一次易丢失的唤醒通知。
4. 后继枚举和完成判定使用同一份已确认图版本。只有范围闭包内所有所需 operation 都有当前有效结果/空结果收据，且无遗漏后继、无待审项、无失败未达成项，Run 才可 completed。
5. 继续使用字段级 lease 更新及提交时的 holder/fence/有效期校验。不能用整份旧 lease 容器覆盖其他 Host 的领取或续租。
6. 当前活跃 Run 期间继续限制普通图编辑；候选修改通过 operation 的 Review。未来若放开无关节点编辑，应独立证明依赖失效规则，本轮不引入额外并发编辑协议。

## 6. 暂停与 Review 正交

Run 增加独立 `paused` 控制位，不把暂停混进 operation 的业务状态，也不复制 `previousStatus`。暂停表示本 Run 不再接受新的执行结果、不再派发新执行；业务状态、输入、报告、Review 和收据保留。

- `run.pause`、`run.resume` 使用与其他用户命令相同的 Editor 权限、用户隔离 requestId、expectedRevision 和 runId。
- pause 在现有权限事务内原子设置 paused、推进 Map revision、写收据，并将该 Run 的所有当前 lease 定向设置为已过期。保留 holder/fence，resume 不把旧期限恢复。
- 仅修改 paused 不够：快速 pause→resume 可能使旧的未过期授权重新有效。用现有过期检查和下一次领取的 fence 递增解决，不再叠加 executionEpoch。
- claim/renew 不推进 Map revision。从快照枚举租约的定向失效必须保持现有 Mongo 事务边界；同图并发领取/续租引发事务冲突重试，不能降成仅凭业务 revision 的无事务写入。
- discover、claim、授权读取、renew、执行结果 commit/fail 一致要求 Run 未暂停；历史收据的无副作用重放可返回已接受结果。
- resume 只针对同一非终态 Run，清除 paused 后按当前输入、结果和 Review 重新计算可执行项；不重新创建 Run，不清空已接受报告，也不自动批准 Review。
- Review 属于 operation。暂停时可以保留、展示和按权限回答审核；批准只改变该 operation 的业务事实，不能清除 Run.paused。其他 operation 是否可执行仍服从 Run.paused。
- 暂停仍是活跃 Run：不允许新 Run 覆盖、普通图编辑、图/Workspace 删除；明确 cancel 后按终态规则操作。

并发以数据库接受顺序裁决：结果先成功则保留该结果，暂停请求按版本冲突刷新；暂停先成功则旧结果和旧失败报告被围栏拒绝。相同暂停请求在用户恢复之后重放只返回当前状态，不再次暂停。

暂停提交即阻止新业务结果接受；当前 DSH 进程在下一次授权/续租失败时退出，不承诺网络中在途模型/工具调用瞬间停止。界面不得把“暂停已提交”描述成已恢复模型执行现场。

## 7. 恢复语义

恢复依据共享 Mongo 中的业务状态，不要求恢复模型上下文、JavaScript 调用栈或中断 token。每次重新领取未完成工作都可启动新的 DSH 会话；已接受报告、用户决定和收据作为业务输入继续使用。

Host 优雅关闭先中止并排空当前 Runtime，再释放 lease；崩溃则等待租约到期，由任意 Host 领取剩余项。关闭客户端或标签页仅退出观察，不暂停或取消 Run。用户显式取消与 Host 退出不同，取消后不能自动恢复。

SessionId 只属于 Host/DSH 执行记录，不决定业务完成，也不作为 operation 或收据身份。DSH 本机历史可保留供诊断，但没有跨 Host 搬运、原生会话加载或模型上下文恢复的本轮要求。

## 8. 客户端与迁移

在 056 客户端上补 scope/until 选择、多个节点/operation 的进度、独立 Review、暂停/继续和输入版本冲突提示。不要把所有节点状态映射成一个 activeNodeId，也不要让某条事实待审隐藏其他新闻的工作。

客户端继续通过公开业务接口访问后端。parse 使用共享资产或明确 URL 来源能力，不重引入客户端绝对路径。尚未接通的内容抓取、管理 UI、产品 SSE 等应继续明确标注，不能因为协议存在就声称已可用。

旧单 operation 数据由显式本机升级工具处理，默认不修改用户数据库；不添加运行时单 operation/operations[] 双路径。活跃旧执行需在升级边界停止领取并处理完/明确终止后再迁移，禁止通过类型断言让旧运行直接进入新协议。迁移细节在实现确认后记录。

## 9. 验收边界

- 单 Host 与多 Host 均完成多 Source、多 News、多 Claim 的范围任务；独立节点与同 Claim 多角度均可并行领取，重叠路径不重复接受结果。
- 分别验证 until=news/claims/verified；scope 不漏到无关子图；共享 Claim 不反向扩大范围；合法空结果不循环执行。
- 一项等待 Review 时另一项继续；批准不清 paused；整体完成不早于新后继发现或最后一个审核。
- 并发领取/续租与 pause、快速 pause→resume、旧 proposal/fail/release、结果与暂停竞争、暂停请求重放均有确定性回归。
- Host 关闭/失联接管保留已接受结果，未提交工作新 Session 重跑；失败/取消不冒充暂停。
- 暂停/等待期间编辑、新 Run、删除权限和用户 requestId 隔离通过；模型/工具可能重做的限制如实展示。
- 跑相关业务回归、全量测试、类型、构建和契约文档检查；记录实际运行结果，历史 058 验收不充当本轮结果。
