## 目标与职责

后端拥有权威发布集合；前端显示候选、输入版本和冻结材料，提交版本化决定。

发布集合由后端与正式发布共用的规则计算。界面解释输入版本、候选与冻结材料，不生成另一套发布算法，也不补造历史正文。

## 拟新增契约

### D03 权威发布预览（C09/C10）

拟新增 `run.publication.preview({ mapId, runId, operationId, reviewId, expectedReviewRevision })`，只读当前待结果审核的 Operation。

返回 `GraphPublicationPreview`：map/run/operation/review 身份、审核版本、specHash、publicationVersion、按端口数量，以及实际发布条目数组。每项带 `(workId,key)`、阶段/槽位/端口/精确类型、`directlySelected` 和 `referencedBy: GraphCandidateRef[]`。条目集合包括被许可的引用闭包；直接入选且被其它条目引用的候选同时保留两类信息。`referencedBy` 表示实际发布集合中的直接引用方，不额外保存整条路径。

查询不新分配节点/边 ID、不返回正式节点 ID、不复制整份候选 payload。现有提案接纳时保存的服务端候选 nodeId 保持原行为，预览不改动它。

将现有 `runCollectPublication` 的集合计算与正式发布前可纯计算的候选引用、端口类型/基数校验收敛为后端共用 `runBuildPublicationPlan()`，查询与正式发布调用同一实现，暂留在既有 `run-state.ts`。关闭引用闭包时不自动补候选，但实际集合仍须满足原发布流程的候选引用可解析性；不新增图引用限制。查询不推进工作、不领取/续租、不保存收据、不抓取外部正文、不改写 GraphDocument。

本轮简化原拟 `candidateDigest`：当前 `run.get` 没有这个字段，不为界面对齐另加一套摘要投影或前端哈希。已接纳的 Work 结果不能覆盖，待结果审核的 Operation 也不再接纳提案。C10 先要求当前 Operation 为 waiting、review 为 pending/result，再把同一 map/run/operation/reviewId+revision/specHash 下的 `(workId,key)` 与保存候选对齐，并核对阶段/槽位/端口/类型；缺失或不符则刷新并暂禁批准。这个约定依赖现有候选不可编辑语义，未来 D-04 候选编辑需另行版本化；前端不拼最终集合。

`publicationVersion` 是后端对规范化相关数据计算的稳定、不透明版本：绑定审核身份/版本、冻结规格、接纳候选内容与选择/闭包结果、相关输入/context 与分支证明；不绑定整图 revision、当前时间或控制租约。使用已有摘要能力，不增加依赖、持久化记录或缓存。

拟给 `review.answer` 增加可选 `expectedPublicationVersion`：仅新结果批准在提供时于现有提交事务/CAS 重试中重算核对；不匹配返回 409 `PUBLICATION_PREVIEW_CONFLICT`，沿现有运行时消息和中文展示入口补文案。C10 的结果批准界面必须提供该值。该可选条件允许 C09 独立合并，未提供者仍遵守现有审核版本/输入/授权规则；本计划不声称所有外部调用都被强制要求先预览。规划审核和拒绝沿用原合同。

预览按现有 Map viewer 权限读取；不要求领取 Run 控制权。批准仍要求 editor，并在协作模式遵守 Run 控制证明；本机模式沿原行为。先识别合法已接纳请求的收据重放，再对新请求做当前状态校验；身份和收据归属检查不省略。审核版本或输入过期仍沿原错误语义，不能通过新版本字段绕过。冲突不改变审核、不创建节点或边。

`app.bootstrap.metadata.capabilities.publicationPreview` 声明服务是否支持此合同，缺省视为不支持，不另造功能开关。已完成/取消/失效、规划审核或已回答审核不提供待发布预览；已发布实际产物由 outputRefs 和保存的候选解释。预览只说明当前集合，不替代正式写入时的权限、分支、引用与库材料校验。

### C09 — 后端发布预览

#### 目标与当前缺口

当前 `OperationReview.vue` 只用最后一份 selection 显示数量；后端实际合并最终阶段的全部 outputs/selection 结果，按 `(workId,key)` 去重，并按冻结规则连带发布引用候选。因此审核者看到的数量可能不完整。C09 先让后端给出可以直接使用的权威集合，C10 再接入审核界面。

当前只有 `plan/result` 两类审核与 `approve/reject` 两个决定，没有人工改规划、改候选、重新选择或逐项批准合同。本批保持这个范围。暂停时允许回答已有审核，结果批准可发布，但后续工作仍暂停；不额外增加“暂停必须拒绝审核”的规则。固定证据库材料沿原合同使用，撤回不改写已冻结材料。

#### 最小实现与职责

1. 新增一个只读查询 `run.publication.preview`，限定当前待结果审核的 Operation，返回 D03 的集合、来源关系、端口统计和版本。
2. 查询与正式发布共用一份 `runBuildPublicationPlan()`，保留最终阶段全部结果、去重、允许的引用闭包、环/非法引用、端口类型与基数规则；正式节点/边物化及其后续校验仍留在发布流程。
3. `review.answer` 的新结果批准可携带预览版本，在写入前核对；同一原请求已成功后，重放仍确认原结果。预览本身不取得任何写权限。

只做这一批，不增加数据库字段、迁移、mapper、缓存、预览租约或新依赖；不改 `OperationReview.vue`、`RunReview.vue` 和会话审核交互，也不处理输入版本/冻结材料的展示。

### C10 — 可核对的审核界面

#### 目标与已核实的缺口

C09 已提供只读预览与可选批准版本条件；当前 `OperationReview.vue` 尚未调用它，仍展示全部候选及最后一份 selection 的数量，批准也未携带预览版本。本图输入只按 nodeId 查当前正文，缺少 revision/类型核对，context 和完整冻结库材料尚未展示。C10 将这些现有信息接到审核页面，不新增后端接口。

第一版仍是整项批准/拒绝，计划审核保持现有行为；不增加候选编辑、部分批准、重新选材或人工重选。沿用中文纸面编辑风格，不改图视图、单页导航或运行编排。

#### 最小界面与行为

| 区块 | 展示与操作 |
| --- | --- |
| 本次将发布 | 按端口显示后端实际数量与条目，区分“直接入选”“连带发布”；同一候选兼具两种关系时同时保留。显示生成阶段/智能体及说明，正文展开阅读；未入选候选折叠。最终阶段的多份选择说明均可读，不再拿最后一份数量代表总集合 |
| 输入材料、上下文材料 | 分别显示冻结 key/端口、节点身份、精确类型与 revision。只有当前节点四项身份（id、revision、typeId、typeVersion）全部匹配才展示对应正文；否则显示原版本、当前版本（若有）及“原版本正文不可用”。不新建历史正文查询 |
| 本步骤冻结证据 | 从当前 Run 的当前 step 读取完整原文、固定 0/1 判断、适用范围、收录理由和四类依据引用；原定义与摘要保留在详情中。候选旁单独列实际 `libraryClaimRefs` 及每条本次使用理由。未实际引用的选材不标成已使用 |

冻结材料只用 `run.libraryClaimSets` 中与 `operation.stepId` 及获权 entryId/contentDigest 对应的快照，不用 `evidence.get` 的当前状态或来源当前节点替换。状态写成“启动时状态”；启动后撤回不改写已获权内容，也不单独阻断批准。库判断 0/1 与意见/结论的评分分别显示，0 不判为空。

审核者可阅读完整冻结正文；旁注说明“智能体按冻结定义的字段白名单和可见项规则读取”，可展开原投影规则，不在前端复制投影算法或声称模型实际看到完整原文。收录依据本批列出保存的引用和人工文本，不再扩展依据逐层阅读；将来如需阅读固定节点依据，可复用现有 `evidence.relations`，不需要新端点。

候选通过 D03 的审核身份/版本、specHash 与唯一 `(workId,key)` 对齐，核对阶段、槽位、端口和精确类型；缺失、重复或不符时提示刷新并禁批准，不略过坏条目、不自行计算闭包。未知业务类型保留原标识和完整字段，不硬套事实/意见模板。已发布 Operation 沿 `outputRefs` 和保存候选说明产物，不调用待审核预览，也不将候选原文冒充后来改动的正式节点现状。

#### 预览读取与批准

每个 `OperationReview` 通过一个小型 `usePublicationPreview()` 持有自身的 data/loading/error、AbortController 与请求序号；预览不进入全局会话缓存。仅对能力明确支持、当前 waiting/pending/result 的审核读取，viewer 也可查看，不以控制权作为读取前置。

- 用户/服务/工作区、Map、Run、Operation、reviewId/revision、specHash 或待审核状态变化时，清空旧预览并取消读取；卸载同样清理。返回后再次核对请求序号和当前身份，迟到成功/失败均不影响后来视图，旧 401 不结束新会话。
- 直接以 `snapshot.revision` 作为重新读取信号，先禁批准再读取；不在前端计算分支 hash。无关图内容变化可能多读一次，但 C09 的内容版本仍稳定；ownershipRevision/控制续租不触发轮询或反复读取。
- 读取中、失败、候选对不上或旧服务未声明能力时，结果批准不可用；显示明确状态和“重新读取预览”或升级提示。规划批准和有权限的拒绝不依赖预览。输入过期由 C09 查询/正式提交校验，前端也不把错版正文当成有效核对材料。
- 点击结果批准时固定当前已展示版本，再使本地预览失效并交会话提交；明确冲突后刷新核对，不自动换版本再次批准。成功则展示原正式结果；结果未知时禁用新批准/拒绝意图，使用现有“重试同一操作”确认。
- `answerReview()` 在等待控制权之前复制意图，校验当前 Map/选中 Run/Operation/review 身份、权限、busy/canRetry；新结果批准要求能力和非空 token。领取后再校验原会话/视图和审核目标，只使用目标 Run 的控制证明；不向后来选中的 Run 提交旧决定。本机仍无需控制租约，暂停不永久禁用已有审核。
- 继续用现有 `submit()/retry()` 固定 requestId、参数、控制证明和 token。原请求重试不重新预览、不生成新 token，也不要求已经发布的审核仍 pending；由后端先确认成功收据。不增加另一套审核重试队列。
