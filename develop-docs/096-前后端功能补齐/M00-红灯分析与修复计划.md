## 1. 已知结论与证据范围

目前有三条已经明确的缺陷机制：两条位于旧测试夹具，另一条位于客户端的授权与快照合并。协作 UI 历史失败仍需受控浏览器用例确认归因，不能把状态层复现直接当作每个 R01/R04/R05 失败的唯一原因。

| 编号 | 问题 | 当前证据 | 结论强度 |
| --- | --- | --- | --- |
| F1 | 消息关闭拒绝，后续 SQLite 与目录清理被跳过 | 既有 Q04 真实故障用例；实际数据库仍可读、目录仍存在，HTTP 已不可达 | 已确认夹具缺陷 |
| F2 | 启动失败后，清理异常遮盖原始启动异常 | 既有 Q02 双故障用例；仅启动失败的对照用例通过，双故障时原错误身份丢失 | 已确认夹具缺陷 |
| S1 | 已领取的新授权被迟到的旧 ownership 快照清掉 | 本轮经真实 `sessionCreateState` 公开方法与内存网关事件边界确定性复现 | 已确认会话状态缺陷；与既有浏览器红灯的直接关联待证 |
| S2 | 保存后的新 payload 和旧分支证明暂时混用，连续编辑可能产生假冲突 | 写入接纳与 Inspector 草稿基线代码的可达时序 | 静态确认存在窗口；尚无本轮定向 UI 复现 |
| S3 | claim 期间切换所选节点，迟到授权仍可能写回新选择 | claim 只校验会话/视图/Map，选择变化不改变视图代次 | 静态边界缺口；不是单节点 R04 的直接解释 |

修复前现场记录：R01 曾在领取授权、正文可编辑后保存超时；R04 在共用 `recoverySavePage` 保存可用性处失败，该 helper 用于多个阶段，不能只凭其行号断言首次重启尚未开始；R05 已执行部分强杀恢复、原数据读取与租约自然到期，随后继续保存超时，未完成三轮。**这些历史记录不证明数据丢失，也未证明后端收到了并拒绝了该次保存请求。** 后续 R04 通过与 R05 新失败阶段另见第 11 节，不覆盖原失败。

独立入口曾出现的 body 为零或无性能报告的前置失败继续单列，尚未查明。F1/F2 解释指定故障注入下的清理结果，不据此归因所有前置失败；本计划不把性能或启动前置问题混入协作保存结论。

## 2. 夹具清理：直接原因

现状文件：[ui-fixture.ts](../../tests/client/ui-fixture.ts)，`fixtureCreateEnvironment()` 内部 `close()`，当前第 144–156 行。

关闭顺序是 Host → API → 本机 provider → 消息 → 数据库连接/SQLite → Mongo → 自有 namespace/broker → 临时目录。当前每一步直接 `await`，任意一步拒绝都会让后面的语句不再执行。

Q04 在 `applicationService.closeMessaging()` 边界注入拒绝，因此后面的 `sqlite.close()` 与 `rm(directory)` 被跳过。这不是缺少一次调用的推测：[ui-fixture-lifecycle.spec.ts](../../tests/client/ui-fixture-lifecycle.spec.ts) 第 153–155 行直接读真实数据库并检查目录存在性；该例同时证明 HTTP 已经关闭，不能扩大表述为所有资源都未释放。Mongo 受同样控制流影响，但尚未取得 Mongo 故障清理的实测证据。

第二条直接原因是第 319 行的 `catch (error) { await close(); throw error }`。一旦 `close()` 拒绝，后面的 `throw error` 不会执行，调用者只收到清理错误，导致启动首错丢失，同时复现 F1 的资源残留。

`closing ??= ...` 的正常并发/重复关闭已通过测试。应保留同一次关闭任务；问题是任务遇首个拒绝就提前结束，不能靠重置 `closing` 再跑一次所有释放步骤解决。

### 拟修复行为

1. 在资源依赖允许的顺序内逐项尝试关闭，记录每项错误，继续处理其余可安全收尾的资源，最后统一报告失败。
2. 关闭成功仍返回成功；单项/多项失败保留原错误对象，不吞掉错误或只留下拼接文本。
3. 只有启动错误时原样抛回；启动与清理都失败时，聚合结果以原启动错误为 `cause`，同时保留清理错误链，供既有身份断言定位。
4. 不确定 Host/写入者是否已结束时，不能为了目录断言转绿就删除仍可能写入的目录。独立资源继续清理，未结束项明确失败；挂起与强制结束需要后续独立期限测试。
5. `fixtureCloseServer()` 明确处理未监听/已关闭服务；启动监听错误要在自身 Promise 中拒绝。是否纳入同一修复，以先行用例证明其真实边界为准。
6. 保持现有返回字段、默认 Mongo、真实 Host 和本机确定性模型能力；不改用新恢复 child 绕过旧夹具。

新恢复夹具可借鉴“逐项收尾、错误汇总、实际进程结束后再删存储”的原则；它没有旧夹具的 Host/DSH 旅程，不能直接替换旧夹具作为修复证据。

## 3. 协作保存：授权被旧快照撤销

现状文件：[client-session.ts](../../apps/ui/state/client-session.ts)，`applySnapshot()` 第 190–200 行，`claimBranch()` 第 522–524 行；[GraphBranchGrant](../../contracts/graph-branch.ts) 已携带 `ownershipRevision`。

确定性时序如下，`R` 为图内容版本，`O` 为占用版本：

1. 会话已保存快照 `R=1/O=0`，其中没有编辑占用；旧 SSE 快照已经生成，尚未交付。
2. `branch.claim` 成功返回 `O=1` 的 grant，会话保存 grant 与分支证明，但已有 snapshot 仍为 `R=1/O=0`。
3. 旧 SSE 快照 `R=1/O=0` 到达。它与会话已有 snapshot 的版本相同，因而没有被防倒退条件拒绝。
4. `applySnapshot()` 用旧快照的 `ownerships` 查找新 grant，查不到便清掉 grant、停止续租。
5. Inspector 的 `owned/editable` 随之为假，保存按钮不可用。后来收到包含占用的新快照，也不会自动重新建立被删除的私有 grant。

本轮临时诊断只使用真实会话实现的 `connect/openMap/selectNode/claimBranch` 公开方法及网关 `watch` 事件回调，改变事件到达顺序；未连接真实后端、未访问组件私有状态。输出为：

| 观察量 | 结果 |
| --- | --- |
| 旧快照交付前/后的本地 grant | 存在 → 消失 |
| 图内容 revision | 不变 |
| 会话 snapshot 的 ownershipRevision | 0 → 0 |
| 已确认 grant 的 ownershipRevision | 1 |
| 内存网关所表示的权威占用 | 仍存在 |
| 分支内容 version | 不变 |
| 交付后的 busy | false |

主代理复核执行退出码为 0。该诊断证明不需要内容版本变化或 busy 残留，就能触发授权丢失；它是状态层漏洞的复现，不是后端租约被错误释放的实测。临时诊断不纳入正常回归，实施前需落成正式测试。

### 拟修复行为

- 快照是否有权撤销一个已确认 grant，必须同时考虑该 grant 的 `ownershipRevision`。低于它的旧占用信息不能因缺少 lease 就清掉新授权；不能把 snapshot 的版本数字改大来伪装一致。
- 同一规则覆盖 claim 与 renew 的确认结果。按快照缺失项撤权的版本条件是 `next.ownershipRevision >= grant.ownershipRevision`，包含相等：同一占用版本下，服务端仍可能因真实到期而不再投影该租约。当前已确认 grant 的 expiresAt 到期、权威续租拒绝与失去权限仍必须使编辑停止，不能通过忽略所有 ownership 更新转绿。
- 续租结果、失败和到期定时器也检查其所属 grant 代次/ownershipRevision；仅匹配 leaseId/fence 不足以防止旧失败或旧定时器清掉同一 lease 后来已确认的续租。
- 接纳 claim 的分支结果时使先前 branch 读取失效，避免旧成功/失败回包推翻新确认。新拥有者同时负责收敛 `branchLoading`，不能因旧 finally 已失效而永久停在加载态。校验所属会话、视图、选择与根集合；切换节点后的迟到 grant 应在正确上下文中释放，不能覆盖新节点。
- `applySnapshot()` 内 Run control 有相似清除逻辑，应增加反例检查；这里只处理共享快照接纳规则，不扩展 Run 功能或整个状态模块重写。
- 图内容版本和占用版本分别保持语义，不能只把二者当成一个简单大小关系。即使内容快照可接纳，也不能用比 grant 更旧的占用事实撤销它。

## 4. 协作保存：草稿和分支证明配对

现状文件：[NodeInspector.vue](../../apps/ui/features/graph/NodeInspector.vue)，`inspectorLoad()`、草稿 watch、`editable/versionChanged`；以及 `client-session.ts` 的 `applyChanges()`、`refreshSelectedBranch()`。

`applyChanges()` 当前只使用写入响应的 `snapshot`，没有接纳同一 `GraphWriteResult.branch`，随后异步刷新分支。Inspector 在保存确认后可能已经用新 payload 重建基线，却读取到旧 branch.version。此时若开始下一稿，迟到的新证明便可能被判断为“服务器数据已变化”，使自己的正常更新变成冲突。

这是连续编辑的独立风险，不能单独解释首次保存前失败的 R04。另外，单纯迟到的旧 `branch.get` 若内容 version 与新 grant 相同，并不会自然产生内容冲突，测试不能假设所有迟到响应必然有害。

### 拟修复行为

1. 优先接纳同次写响应中配对的 snapshot 与 branch。匹配 Map、选择/根集合、`mapRevision/rootRevisions`，这些匹配用于验证同次响应内部的一致性。若当前会话已有更新的状态，不能拿旧响应覆盖它或与它混配；已提交成功的命令仍是成功，保留当前状态并重新取得可用证明。仅根 revision 相同不证明旧分支可复用，后继与边也参与分支 version。
2. `GraphWriteResult.branch` 在合法重放等情形可以缺省；缺省时通过公共读取取得一致证明，配对完成前不开放新的编辑基线，保留已有草稿。目标已删除时清理无效选择，选择/视图已经变化时忽略旧结果，不对不存在的根无限重读。
3. `refreshSelectedBranch()` 的读取代次同时服从已接纳命令与选择代次；旧成功或失败均不能污染新确认。
4. Inspector 只在 payload 与证明属于同一已接受基线时重建草稿。不能把 `branch.mapRevision === 当前图 revision` 变成始终生效的编辑门禁或内容冲突判据；无关分支的图级版本变化不能无条件制造当前分支冲突。配对检查用于建立已接受基线，不能破坏独立分支可并行编辑的合同。
5. 真正的外部内容变化仍保留旧草稿并阻止旧证明覆盖。禁止为了解除禁用直接把脏草稿的 `baseVersion` 改成最新值，也不能静默重新加载丢弃草稿。

| CS-03 | claim 期间扣住旧 branch.get，随后放行成功或失败 | 新确认不被覆盖/清空，加载态正常结束；同版本旧成功不会被错写成内容冲突；切到另一节点的迟到授权不污染选择 |
| CS-04 | 真实 UI，relay 扣住 claim 前原始 SSE snapshot；claim 成功且正文可编辑后放旧帧 | 草稿和合法编辑权保持；捕获真实 graph.apply 请求并独立核对保存结果，再放权威新帧 |
| CS-05 | 保存成功后扣住 branch 刷新，立即开始下一稿；写响应到达前已有新快照，或合法响应无 branch | 不以旧证明建立新草稿；不混配/倒退当前状态、不把已提交成功判为失败；目标删除/切换时结束旧读取，就绪后可继续保存，不产生自身更新的假冲突 |
| CS-06 | 外部真实改动同一分支；无关独立分支另作对照 | 前者保留草稿并明确冲突，后者不破坏当前可保存状态；旧 expectedVersion 仍被拒绝 |
| CS-07 | 原 R01/R02/R04/R05，保留约定轮次 | 十轮争用/二十次独立写、三轮优雅重启/真实强杀均完成；沿用原账号/数据/资产/收据，协作旧租约自然到期 |

浏览器诊断要区分：没有发出保存请求、使用了旧 expectedVersion、使用了旧 lease、后端真实拒绝。记录固定枚举、阶段与布尔值；不输出 token、正文、原始网络载荷或异常。SSE 屏障只扣住已由真实后端产生的原始帧，不伪造成功或新快照；不能用 sleep、追加数据库读操作拖慢时序或反复重跑来作为修复。

## 7. 建议修复次序与提交边界

以下是三次修复提交的边界。用户已授权并实施第 1 批夹具与第 2 批 S1 修复，尚未创建提交；第 3 批 S2 仍为候选方案。原 24 个功能交付建议不在本次修复中擅自改号，正式整理提交时需同步总计划及台账。

| 顺序 | 建议标题 | 同次必须带的先行测试与验收 |
| --- | --- | --- |
| 1 | `fix(test): complete fixture cleanup and preserve startup failures` | FX-01–04 与相关真实集成回归；原两红转绿、原正常幂等不退化。先修设施，让后续失败能可靠收尾和归因 |
| 2 | `fix(ui): preserve confirmed grants across delayed snapshots` | CS-01–04；授权接纳、失权反例、选择代次隔离和真实 SSE 顺序；先确认与 R01/R04/R05 红灯的关联，不以单次 R 通过代替根因证据 |
| 3 | `fix(ui): bind edit drafts to matching branch proofs` | CS-05/06，连续编辑与合法缺省 branch、重放/迟到读；再完整执行 CS-07，所有自身更新假冲突与真实外部冲突分开验收 |

每个提交均先写并运行自己的测试，再修对应实现，最终一起交付可审阅变更和记录；不是将全部回归推迟到最后。两个会话提交触及同一集成热点，串行实施。若 S2 的定向复现不能成立，应校正假设和计划，不能为按表完成而无依据改实现。

挂起 disposer 的期限/看门狗、启动中 SIGTERM/父 IPC 断开、CLI 原始错误输出等是相邻静态风险，仍归后续 Q04/Q05/Q07 的独立先行批次；不把上述三次修复完成宣称为整个 M00 完成。
