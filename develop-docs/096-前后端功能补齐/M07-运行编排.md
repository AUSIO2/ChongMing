### C15 — 两入口共用运行草稿

#### 当前差异与第一版交互

两个入口实际支持范围相同：单个input端口，context只能是可选端口；1:1/1:N按each处理，N:1/N:M按all并检查数量。区别在于Inspector自己保存转换/mode/regenerate并直接startRun，完全绕过选材；顶部另有批选对话框和runEvidence。顶部每次重置regenerate但保留mode，侧栏两项又各自保留，初始化策略也不一致。

C15将两边都引向一个RunComposer，入口只提供初始化意图：

| 入口/动作 | 确定行为 |
| --- | --- |
| 顶部“运行转换” | 保留批量入口：以第一个现有简单转换及其符合类型的节点预填，用户在统一表单中核对/改选；不因当前画布选中节点而暗改批量范围 |
| 节点侧栏 | 保留精确转换选择，按钮改为“配置并运行”，传当前已保存节点和所选转换打开相同表单；不再直接提交。侧栏移除独立mode/regenerate表单和plan构造 |
| 新开草稿 | 两入口统一默认为人工审核、regenerate=false、固定库材料未选；不继承另一个目标的旧模式/选材。关闭后重开是新草稿，不增加草稿历史或持久化 |
| 表单内 | 统一编辑转换、节点范围、处理方式、重新生成及显式固定选材；切换转换只保留仍符合精确输入类型的节点，不自动补选其它类型节点 |
| 开始处理 | 构造一份独立单步参数，经Page转交原session.startRun，后端继续冻结定义、输入和材料。打开、检查或选材都不发run.start |

同一个输入选择/转换/mode/regenerate/材料形成相同业务参数；两个入口的不同默认范围是明确的seed差异，不强行做成同一默认。step/Run/request有随机身份，两次独立创建不能断言字节完全相等，测试须使用同一固定草稿或排除这些生成身份。

正文编辑和运行草稿分开：节点入口继续保留原脏稿/运行占用门禁；顶部仍处理已保存数据，不保存或消费未保存正文。统一表单改选起点不调用session.selectNode，不重挂Inspector，不自动保存/恢复正文或改变视图。原固定后继创建、人工来源、C06引用编辑和普通节点类型地位保持，不扩自由连线或只允许Claim的特例。

#### 归属与选材

- Page只拥有本次打开的user/service/workspace/map身份和初始选择；RunComposer拥有本次对话框的一份typed运行草稿和一份evidenceCreateSelection。关闭/切Map/工作区/服务/用户时释放窗口及选材查询，不取消已有Run或释放其控制权。
- run-draft.ts只负责独立草稿、当前单步类型/数量验证与提交构造，不访问网关、分支或控制权。复用graphCreateRunPlan和evidenceBindClaimsToStep，不另做执行/发布校验器；runSeedFromSelection只有确有重复再抽，不机械添加转发helper。
- 材料继续显式选择、每步最多32条，传entryId/contentDigest；不默认选整个库，不自动继承节点已有libraryClaimRefs，也不把固定库来源节点塞进scope/input/context。可选context仍显式传空绑定，不在C15补选择器。
- 选材targetKey绑定精确转换及所选节点的ID/类型/内容revision，连同原身份、Map与库能力隔离；换转换/目标或所选正文变版时清旧材料并提示重新核对。不以整图同步revision为key，避免无关节点变化或续租清材；仅改mode/regenerate不清材料。
- 无库能力时不创建活动库查询，显示服务未提供并保留同一运行路径；取消/卸载沿原选材状态取消请求，不另建缓存、查源队列或轮询。选材后被撤回等并发有效性仍由原启动冻结规则权威校验，不新建自动替换材料逻辑。

#### 原请求保护的一处必要门禁

现有顶部homeOpenRunDialog直接session.clearError，且两入口按钮/session.startRun没有完整canRetry门禁。原写入结果待确认时，新运行意图可能清掉旧重试记录。此为C15需先测再修的行为缺口，不把它混同为纯表单搬迁。

两入口打开/编辑/新提交在busy或canRetry时锁定；Page不以新对话框清除待确认意图，session.startRun补最小canRetry拒绝条件。重试只调原session.retry，不能重新runBuildSubmission或分配新Run/request来确认。关闭窗口不清全局重试，取消窗口也不表示取消已提交的Run。

session仍独占branch.get/版本核对、租约、Run ID、控制权接管和原请求重放。Composer提交时复制nodeIds/计划/材料，等待启动期间锁定表单；不把可变Vue草稿交给异步分支领取后才读取。不重构通用session生命周期或扩大M00恢复资格。

### C16 — 通用多端口与 DAG 编排

#### 第一版交互

C16扩展C15的同一表单和草稿，默认仍是一张步骤卡；用户“添加步骤”后形成纵向列表。每卡选择精确转换、各input/context来源、分组与空输入策略，提交前显示完整计划摘要。依赖只在有序表单中选择前序步骤，不做拖拽节点图或另一个执行引擎。步骤依赖不是证据图的关系，不新增任意牵线。

| 区域 | 第一版行为 |
| --- | --- |
| 步骤 | 添加/删除、精确转换、直接依赖；步骤ID创建后稳定，显示顺序改变或删除其它卡不重编号。被引用的步骤先解除引用/依赖再删除，不级联丢弃用户草稿 |
| input/context端口 | 按转换声明逐个显示类型/版本及min/max，每端口只选一种来源：当前图一组保存节点，或一个直接依赖步骤的一个输出端口；可选端口也保留明确空绑定 |
| 前步产物 | 只列类型版本匹配的前序输出端口，选择时明确加入并显示所需直接依赖；不能取消仍被端口引用的依赖。其它依赖可只表达先后顺序；不预填未来节点ID或使用未发布候选 |
| 分组 | each（逐个）、all（全部一起）、explicit（显式成员表）；按每组各端口数量核对，context不在成员表内，每组共享其已选上下文 |
| 材料 | 每个步骤各有明确的固定库选择，仍每步最多32条；只激活当前编辑步骤的候选查询，切卡保留各步选择，不默认复制其它步骤材料 |
| 确认 | 汇总所有用户明确选择的同图scope来源，展示去重运行范围、各步骤/来源/依赖/分组/材料，再沿C15统一提交和原请求确认 |

只有一种steps数组作为权威草稿，首步seed继续服务顶部/节点入口；不并行维护“旧单步”和“高级计划”两套状态。新草稿仍人工审核、不重新生成。已有简单单步数据与参数语义保持；复杂转换先预填一个匹配input，其他必填端口/上下文明确待选择，不自动将同一节点复制到所有同类型端口。

#### 必须按真实后端规则表达

- 全部input/context端口都须各有一份绑定，包括可选空端口。一个端口不能混合scope与step来源，或拼接多个输出端口；前步来源必须是直接dependsOn及其精确输出类型，不能借任意传递祖先。
- 只有前步已完成Operation的正式outputRefs会进入下步；用户选的是“步骤/输出端口”，启动前并无未来节点ID。实际产物数量由运行结果确定，不能用输出定义的单组min/max冒充汇总数量已经满足下步。
- scope包含所有input和context中明确选择的保存节点，去重并显示，不含库来源节点或未来产物。context正文只读也必须进入同Map运行范围/版本分支授权，后继分支仍按现有规则保护；不承诺上下文能旁路占用，不跨Map挑选普通节点。
- each仅在恰好一个input端口时可用，即使另一个input可选也不例外；每个单节点组仍须符合端口数量。N:1/N:M不一律禁止each，例如min=1仍可逐个，默认按数量选择合适规则。all/explicit逐组逐端口检查已知数量和类型。
- explicit成员必须是相应input来源里实际存在的节点ID；首版仅对所有input都是scope来源时开放，前步产物步骤用each/all。组间可复用成员，不强制互斥或全覆盖；单组单端口不允许重复，不能悄悄加入未绑定节点。context不参与members。
- onEmpty只决定整步无输入组/全部输入为空时skip或fail，不替代某必填input/context缺失的数量校验。动态产物的实际基数仍由后端实例化时核对，表单显示数量尚待运行，不新造前端预执行。
- 计划1–64步；节点数量沿各端口定义，不统一套“64节点”。材料32/步、Agent阶段数和maxSlots沿各自现有合同，不能混用限制。草稿检查缺依赖/自依赖/环，后端继续权威验证。

选材仍由各步骤持有原evidenceCreateSelection状态，稳定stepId保持切卡草稿，仅当前卡激活读取，不新建材料缓存层。改某步目标时清该步及依赖它的相关材料，保留无关分支；mode/regenerate不清材。当前图已选节点变版/能力失效继续沿C15处理；改材料本身不反过来清掉材料。构造层只保存每步精确refs，不把材料浏览状态写入GraphRunPlan。
