## 1. 交付目标与边界

补齐 095 的 F01–F20，形成可审查的完整业务路径：用户能管理图和关系、配置精确定义与智能体、从统一入口编排运行，审核实际将发布的内容，追查证据与历史，并处理权限、占用、冲突和失败恢复。

计划分 **12 个模块、22 个交付批次**；M00 的 C01 建议拆成 C01a–C01c，因此当前为 **24 个建议 Git 提交**。每批严格按“先写并运行测试→确认目标缺口→实现→回归”的顺序推进，具体门槛见第 8 节。最终提交同时包含该行为所需的源码、定向测试和文档更新；最后一个提交负责跨模块验收，不能把前面各批的测试推迟到最后。实施时以现有模块归属为准，不新增独立 Mapper 或统一大状态仓库。

**本轮范围**：已有公开能力的前端补齐，以及为正确使用这些能力所必需的服务能力声明、空图改名、共享定义目录、发布预览和历史目录契约。

### 共享约束

1. 远端事实仍归服务端/现有会话；草稿、选中、相机和阅读位置归各窗口。组件不自行拼接“领取授权→写入→释放”的业务链。
2. 同一工作区中的跨 Map 身份必须带 workspaceId/mapId/nodeId；固定材料还必须带 revision 或 contentDigest。不得以摘要或相同正文合并业务身份。
3. 新增 `libraryClaimRefs` 使用显式理由；**省略表示保留，空数组才表示清除**。普通 payload 保存不得误删元数据。
4. 来源锚点绑定来源 revision/字段/行范围/quote，原文变化后保留旧摘录并提示，不能把旧行号高亮到新版正文。
5. 类型版本与 Agent 精确配置版本沿用现有规则，不把 Agent 的 revision=0 擅自改成从 1 起算。不修改已发布包，不自动把历史 Run 绑定到最新定义。
6. viewer/editor/owner、hostAdmin、服务能力是不同维度。模型/Host 内部令牌不进入 Renderer；本机无客户端租约时不得调用 claim/renew/release。
7. 不确定的写入结果只用原 requestId、原参数重试；明确 409 后重新读基线，由用户审阅后发起新请求。收据重放检查仍先于新写入的版本/租约校验。
8. 所有异步结果按用户、连接、工作区、图、目标和请求代次隔离；切换后迟到结果不能改写新窗口。取消请求不等于撤销已提交写入。
9. 后端校验是权威。前端提供及时输入校验，不复制完整发布算法、权限引擎或 JSON Schema 验证器。
10. 使用冻结材料时，区分“完整冻结记录”和“智能体可见投影”；展示全文不能被描述为模型实际看到的全部字段。
11. 节点合法后继由当前精确类型定义决定，关系由明确创建/转换动作形成；后端有通用边能力不等于主界面应提供任意牵线。业务引用写入声明字段并派生引用，不能用普通 reference 边替代。

- 从已明确的集成基线建立 `codex/frontend-parity-*` 功能分支；名称是建议，本次不创建分支。
- 不使用 `git add .`、`git commit -am` 或整库格式化夹带其他工作；按提交文件清单逐文件/逐块暂存。
- 测试编写和首次执行必须先于本批生产实现；“同一提交包含生产行为和相应测试”只规定最终交付单位，不改变测试先行顺序。最终提交应通过相关检查，不把已知失败的实现合入集成分支后再补测试。
- `client-session.ts`、`WorkspacePage.vue`、公共契约/客户端白名单是集成热点。同文件变更由集成人串行合并，不能因模块可并行而同时覆盖文件。
- API 提交必须贯通契约、服务、HTTP、客户端校验和实际 IPC/CLI 路由；不能只在 TypeScript 联合中增加名字。
- 过大提交可在本编号下拆成 `Cxxa/Cxxb`，但按可独立运行的行为拆；同步更新依赖和台账，不能拆出接口白名单与处理器不一致的中间状态。
- 发布不可变定义或删除数据图之后，Git 回退不会恢复远端业务数据。回退方案以关闭新入口/恢复匹配版本为主，已发布定义用后续新版本纠正。

## 8. 验证门禁与完成定义

### 测试先行顺序（全部 C01–C22 适用）

1. **用例先行**：先列本批行为、输入、预期结果和对应 F 项，再新增或扩展可执行测试。按实际风险覆盖正常路径、权限/版本/占用和失败恢复；只有确实覆盖目标行为的既有测试才可复用。
2. **运行并确认缺口**：修改本批生产代码前运行定向测试，记录用例名、命令、预期、实际结果和失败原因。功能补齐必须先得到目标行为缺失导致的失败；缺依赖、类型/导入错误、服务未启动等环境问题不算有效红灯。新 API 优先从现有公开协议边界验证缺失行为，不以导入不存在的私有函数报错代替行为验证。
3. **最小实现转绿**：有上述证据后才修改生产实现，以同一用例验证目标行为已满足。不得删除、跳过或削弱断言来获得通过；需求有依据地改变时先更新用例及台账。
4. **保持通过再整理**：定向测试通过后才整理实现，并再次运行受影响用例；按本批风险补足契约、真实适配器、浏览器及类型检查。只有新增变更、失败或未解决风险才扩大/重复测试。
5. **交付留证**：台账包含实现前和实现后的两次结果及命令，最终提交同时包含测试、实现和记录。未运行或环境受阻的项目明确列出，不能标记为通过或完成。
