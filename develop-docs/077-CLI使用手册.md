# CLI 使用手册：按用例（UC）操作

适用版本：当前 077 实现，2026-09-29。面向人工操作、Shell 脚本和外部 Agent。CLI 通过认证 HTTP API 操作数据，使用 SSE 接收事件；模型和工具由服务端 Host/DSH 执行。

本文中的 UC 编号仅属于本手册。主流程为 UC-01 → UC-02 → UC-03 → UC-04 → UC-05 → UC-07 → UC-09/10/11。其他用例按需执行。

## 先区分本地模式与协作模式

**本地模式不需要领取编辑权、领取 Run 控制权或续租。** `local:serve`（包括桌面内置本机服务）在本机事务内处理提交。已有节点仍携带分支内容版本，运行中的分支仍受保护；多个本地客户端改同一分支时，旧版本提交会被拒绝。

| 操作 | 本地服务 | 协作服务 |
|---|---|---|
| 编辑已有分支 | branch proof + changes | 再带编辑 lease |
| 启动 Run | branch proof + scope + plan | 再带编辑 lease |
| 暂停/继续/取消/审核 | runId 及业务参数 | 再带 control proof |
| 客户端领取、续租、释放 | 不使用，接口返回 `CLIENT_LEASES_DISABLED` | 使用 branch.* / run.control.* |

以 `app.bootstrap.data.metadata.clientLeases` 判断：`none` 为无需客户端租约，`required` 为需要；旧服务缺省按 required 处理。策略由服务启动入口决定，不根据 URL 是否为 localhost 推断，也不能通过某次请求关闭服务端校验。Host 内部 Work 授权由系统自动管理，无需 CLI 操作者续租。

## UC-01 连接服务并准备操作环境

**参与者 / 前提**：拥有用户 Token；在仓库根目录执行，已安装项目依赖。示例使用 Bash、Node.js 24+ 和 `jq`。`jq` 用于生成和读取 JSON，并非 CLI 本身的依赖。没有服务时先执行 UC-19。

**步骤**：先查看离线帮助，再设置服务与 Token 文件路径。

```bash
npm --silent run headless -- --help

CM_API='http://127.0.0.1:4320'
CM_TOKEN_FILE='/absolute/path/to/user-token'
umask 077
CM_CASE="$(mktemp -d "${TMPDIR:-/tmp}/chongming-cli-XXXXXX")"

uuid() { node -e 'process.stdout.write(require("node:crypto").randomUUID()+"\n")'; }
cm() {
  npm --silent run headless -- "$@" --url "$CM_API" --token-file "$CM_TOKEN_FILE"
}

cm read app.bootstrap > "$CM_CASE/bootstrap.json"
jq '.data.identity' "$CM_CASE/bootstrap.json"
CM_CLIENT_LEASES="$(jq -r '.data.metadata.clientLeases // "required"' "$CM_CASE/bootstrap.json")"
# 只有协作模式需要客户端 holder；两个客户端不得共享同一个 holder。
if [ "$CM_CLIENT_LEASES" = required ]; then CM_HOLDER_ID="$(uuid)"; fi
```

`--url` 可替代为 `CHONGMING_GRAPH_API`，默认地址为 `http://127.0.0.1:4320`；凭据也可用 `CHONGMING_USER_TOKEN`。用户 Token 和 Host 的 `CHONGMING_DATA_TOKEN` 用途不同。CLI 每次从指定来源读取凭据，没有持久登录会话。

后续示例使用以下**本手册的 Shell 辅助函数**保存写入请求。它不是新增 CLI 子命令：首次调用保存方法、参数和 request-id；同名调用只能重发同一请求。一个操作名不要由两个进程同时使用。

```bash
cm_submit() {
  local operation="$1" method="$2" input_file="$3"
  [[ "$operation" =~ ^[a-zA-Z0-9_-]+$ ]] || return 2
  local prefix="$CM_CASE/$operation"
  if [ ! -f "$prefix.request-id" ]; then
    cp "$input_file" "$prefix.params.json" || return
    printf '%s\n' "$method" > "$prefix.method" || return
    uuid > "$prefix.request-id" || return
  fi
  if [ "$(cat "$prefix.method")" != "$method" ] || ! cmp -s "$input_file" "$prefix.params.json"; then
    printf '%s\n' '该操作名已绑定其他输入；新意图请使用新的操作名。' >&2
    return 2
  fi
  cm dispatch "$method" --request-id "$(cat "$prefix.request-id")" --input "$prefix.params.json"
}
```

一个 UC 中失败后先停止后续步骤，按 UC-17 处理。自动化脚本应检查每次命令退出码，并对 `claimed/busy` 再作业务判断。重新执行整段 UC 可能生成新的节点/Run ID；重试写入时只重发保存的请求。

**结果**：普通查询输出 `{ "ok": true, "data": ... }`；写入输出另含 `requestId`、`replayed`。本文所有 `--input` 文件只包含 **params 对象**，不含外层 `method/requestId/params` 信封。使用 `npm --silent` 可避免 npm 的脚本标题混入 JSON。

## UC-02 选择或创建工作区与数据图

**参与者 / 前提**：UC-01 已完成。查询需要相应工作区的 Viewer 及以上权限，创建图需要 Editor/Owner。创建工作区的用户成为该工作区 Owner。

**步骤 A：选择已有资源。**

```bash
cm read workspace.list > "$CM_CASE/workspaces.json"
jq '.data.items[] | {id, name, role}' "$CM_CASE/workspaces.json"
```

选择实际 UUID 后，使用以下查询；示例中的 UUID 占位内容必须替换。

```bash
CM_WORKSPACE_ID='替换为工作区UUID'
jq -n --arg id "$CM_WORKSPACE_ID" '{workspaceId:$id}' > "$CM_CASE/workspace-query.json"
cm read workspace.get --input "$CM_CASE/workspace-query.json" > "$CM_CASE/workspace.json"
cm read map.list --input "$CM_CASE/workspace-query.json" > "$CM_CASE/maps.json"
jq '.data[] | {id, name, nodeCount}' "$CM_CASE/maps.json"
CM_MAP_ID='替换为图UUID'
```

**步骤 B：从新工作区开始。** 此分支可以替代步骤 A；`agentSource: "library"` 复制已初始化的共享 Agent 库及定义。

```bash
CM_WORKSPACE_ID="$(uuid)"
jq -n --arg id "$CM_WORKSPACE_ID" \
  '{id:$id,name:"CLI 示例工作区",description:"UC 操作示例",agentSource:"library"}' \
  > "$CM_CASE/workspace-create.json"
cm_submit uc02-workspace workspace.create "$CM_CASE/workspace-create.json" > "$CM_CASE/workspace-created.json"

jq -n --arg id "$CM_WORKSPACE_ID" '{workspaceId:$id}' > "$CM_CASE/workspace-query.json"
cm read workspace.get --input "$CM_CASE/workspace-query.json" > "$CM_CASE/workspace.json"
CM_MAP_ID="$(uuid)"
jq --arg id "$CM_MAP_ID" '.data | {workspaceId:.id,expectedRevision:.revision,id:$id,name:"CLI 示例图"}' \
  "$CM_CASE/workspace.json" > "$CM_CASE/map-create.json"
cm_submit uc02-map map.create "$CM_CASE/map-create.json" > "$CM_CASE/map-created.json"
```

两种路径最后都可读取图：

```bash
jq -n --arg id "$CM_MAP_ID" '{mapId:$id}' > "$CM_CASE/map-query.json"
cm read map.get --input "$CM_CASE/map-query.json" > "$CM_CASE/map.json"
jq '.data | {mapId,revision,ownershipRevision,nodes,runs,ownerships,runControls}' "$CM_CASE/map.json"
```

**结果 / 分支**：新图的 `runs` 为空数组。工作区/资产列表分页结果为 `{items,nextCursor}`，有下一页时将 `nextCursor` 原样作为下次 `cursor`，`limit` 为 1–200；`map.list` 直接返回数组。创建图的 `expectedRevision` 取工作区版本。

## UC-03 查阅注册类型和可执行转换

**参与者 / 前提**：Viewer 及以上；已选择工作区。

```bash
cm read definition.get --input "$CM_CASE/workspace-query.json" > "$CM_CASE/definitions.json"
jq '.data.catalog.dataTypes[] | {id,version,title,schema,successorTypes,references}' "$CM_CASE/definitions.json"
jq '.data.catalog.transitions[] | {id,version,title,ports,cardinality,execution,review}' "$CM_CASE/definitions.json"
```

**结果**：节点引用精确的 `typeId/typeVersion`，转换引用精确的 `id/version`。`successorTypes` 声明允许的后继类型；实例之间的实际关系另由 `edges` 表达。

读取精确包时给 `definition.get` 同时传 `packageId` 和 `packageVersion`，值来自 `.data.catalog.packages[].ref`。不要把类型 ID 当成包 ID。

后面的节点和 Run 示例采用默认包的 `factcheck.claim@1`、`factcheck.verify-claim@1`。执行前检查目录确有这些定义；自定义业务应替换类型、payload、转换和端口，而不是只替换显示名称。

## UC-04 创建独立数据节点

**参与者 / 前提**：Editor/Owner；图和 `factcheck.claim@1` 已存在。此步骤生成新的 `CM_NODE_ID`。

```bash
CM_NODE_ID="$(uuid)"
jq -n --arg map "$CM_MAP_ID" --arg node "$CM_NODE_ID" '{
  mapId:$map,
  branch:{rootIds:[$node],expectedVersion:null},
  changes:{nodes:{put:[{id:$node,typeId:"factcheck.claim",typeVersion:1,
    payload:{content:"待核查的事实陈述",category:null}}]}}
}' > "$CM_CASE/node-create.json"
cm_submit uc04-node graph.apply "$CM_CASE/node-create.json" > "$CM_CASE/node-created.json"
jq '.data | {createdNodeIds,branch}' "$CM_CASE/node-created.json"
```

**结果 / 分支**：`expectedVersion: null` 仅用于创建本次全新的独立分支，不需要先领取一个尚不存在的分支。它不能修改已有节点、连接旧节点、删除数据或改图名。声明的新节点必须从本次根沿 successor 可达；多棵新树应列出各自的根。

## UC-05 编辑分支并保存修改

**参与者 / 前提**：Editor/Owner；已有 `CM_NODE_ID`。按 UC-01 返回的服务能力选择下面一条路径。

### 本地模式：读取分支版本 → 保存

```bash
jq -n --arg map "$CM_MAP_ID" --arg node "$CM_NODE_ID" \
  '{mapId:$map,rootIds:[$node]}' > "$CM_CASE/branch-query.json"
cm read branch.get --input "$CM_CASE/branch-query.json" > "$CM_CASE/local-edit-branch.json"
jq -n --arg map "$CM_MAP_ID" --arg node "$CM_NODE_ID" \
  --slurpfile branch "$CM_CASE/local-edit-branch.json" '{
  mapId:$map,
  branch:{rootIds:$branch[0].data.scope.rootIds,expectedVersion:$branch[0].data.version},
  changes:{nodes:{put:[{id:$node,typeId:"factcheck.claim",typeVersion:1,
    payload:{content:"已修改、准备核查的事实陈述",category:null}}]}}
}' > "$CM_CASE/local-node-edit.json"
cm_submit uc05-local-save graph.apply "$CM_CASE/local-node-edit.json"
```

没有 holder、lease 或续租步骤。分支版本不会因时间流逝而过期；内容发生变化才会产生版本冲突。保存成功后下一次编辑应采用新的分支版本。版本冲突时先读取并合并内容，不要直接换版本号覆盖。

### 协作模式：领取 → 检查结果 → 保存

以下领取、续租和释放步骤仅用于协作模式。本地模式跳到 UC-06 或 UC-07。协作租约默认 30 秒，按响应的 leaseMs/expiresAt 为准，准备好内容后再领取。

```bash
jq -n --arg map "$CM_MAP_ID" --arg node "$CM_NODE_ID" --arg holder "$CM_HOLDER_ID" \
  '{mapId:$map,rootIds:[$node],holderId:$holder}' > "$CM_CASE/edit-claim.json"
cm_submit uc05-claim branch.claim "$CM_CASE/edit-claim.json" > "$CM_CASE/edit-claim-result.json"
jq -e '.data.status == "claimed"' "$CM_CASE/edit-claim-result.json"
# 若上一步失败，停止；读取 .data.ownership 查看占用，不能继续保存。
jq '.data.grant' "$CM_CASE/edit-claim-result.json" > "$CM_CASE/edit-grant.json"
jq '{leaseId,holderId,fence}' "$CM_CASE/edit-grant.json" > "$CM_CASE/edit-lease.json"

jq -n --arg map "$CM_MAP_ID" --arg node "$CM_NODE_ID" \
  --slurpfile grant "$CM_CASE/edit-grant.json" --slurpfile lease "$CM_CASE/edit-lease.json" '{
  mapId:$map,
  branch:{rootIds:$grant[0].branch.scope.rootIds,expectedVersion:$grant[0].branch.version},
  lease:$lease[0],
  changes:{nodes:{put:[{id:$node,typeId:"factcheck.claim",typeVersion:1,
    payload:{content:"已修改、准备核查的事实陈述",category:null}}]}}
}' > "$CM_CASE/node-edit.json"
cm_submit uc05-save graph.apply "$CM_CASE/node-edit.json" > "$CM_CASE/node-edited.json"
```

**协作模式长时间编辑**：在租期内调用续租。每次新的心跳使用新的请求 ID；只有重试同一次心跳才复用它的请求 ID。

```bash
jq -n --arg map "$CM_MAP_ID" --slurpfile lease "$CM_CASE/edit-lease.json" \
  '{mapId:$map,lease:$lease[0]}' > "$CM_CASE/edit-lease-params.json"
cm_submit "uc05-renew-$(uuid)" branch.renew "$CM_CASE/edit-lease-params.json" > "$CM_CASE/edit-renewed.json"
```

续租只更新期限，**不代表旧草稿已采用最新内容**。再次写入前，读取 `branch.get {mapId,rootIds}`，将返回版本与草稿基线比较；有变化先合并草稿，再构造新请求。`graph.apply` 的节点 `put` 是完整 payload 替换，要保留未编辑的字段。

**结束编辑：**

```bash
jq -n --arg map "$CM_MAP_ID" --slurpfile lease "$CM_CASE/edit-lease.json" \
  '{mapId:$map,lease:$lease[0]}' > "$CM_CASE/edit-lease-params.json"
cm_submit uc05-release branch.release "$CM_CASE/edit-lease-params.json"
```

**结果 / 异常**：同根、祖先/后继以及共享实际后继的分支互斥；同一用户两个 holder 也互斥。领取占用分支返回 `ok:true,data.status:"busy"`，CLI 退出码仍是 0，必须检查 status。失租写入返回 `BRANCH_LEASE_LOST`，不要继续续用旧 proof。释放失败时租期仍会回收；如果已到期，再次领取是新操作。

## UC-06 修改关系或删除节点

**参与者 / 前提**：Editor/Owner；取得覆盖完整影响范围的 branch proof。协作模式还需领取相同根集合的租约；本地直接提交。以下为 `changes` 的形状说明，UUID 字符串需替换；完整 `graph.apply` 参数参见 UC-05。

| 目标 | `changes` 内容 |
|---|---|
| 添加或更新关系 | `{"edges":{"put":[{"id":"关系UUID","kind":"successor","from":"上游UUID","to":"后继UUID"}]}}` |
| 删除关系 | `{"edges":{"remove":["关系UUID"]}}` |
| 删除节点 | `{"nodes":{"remove":["节点UUID"]}}` |
| 改图名 | `{"name":"新图名"}` |

`successor` 要符合已注册类型的后继许可，并保持无环；`reference` 不扩张后继闭包，但会影响相关版本和修改范围。

连接两个既有分支应以多个根取得覆盖全部端点的分支版本；协作模式还应一次领取这组根。删除节点还涉及级联关系的另一端；只选一个子节点可能覆盖不足。被 payload 引用的节点应在同一授权修改中解除引用后再删除。图名修改需要范围覆盖全部节点。

**结果 / 异常**：保存返回新分支版本。超范围返回 `BRANCH_SCOPE_CONFLICT`；不支持把多次局部领取拼成一个租约，也没有持有中原子追加根的公开命令。需要更大范围时，释放原授权后以完整多根集合重新领取，并重新读取内容基线。删除后的节点/边 ID 不得复用。

## UC-07 启动一次转换运行

**参与者 / 前提**：Editor/Owner；类型和转换已发布、绑定 Agent 可用；有执行该部署任务的 Host。运行会调用已配置模型和工具。协作模式下，应结束 UC-05 的编辑会话后再重新领取。

**步骤**：两种模式都先准备有限 plan。这里使用默认核查转换；`context` 的空新闻端口也是显式声明。

```bash
jq -n --arg node "$CM_NODE_ID" '{steps:[{
  id:"verify",transitionRef:{id:"factcheck.verify-claim",version:1},dependsOn:[],
  input:[{port:"claim",source:{kind:"scope",nodeIds:[$node]}}],
  context:[{port:"news",source:{kind:"scope",nodeIds:[]}}],
  grouping:{mode:"each"},onEmpty:"fail"
}]}' > "$CM_CASE/run-plan.json"
```

### 本地模式：读取版本并直接启动

```bash
jq -n --arg map "$CM_MAP_ID" --arg node "$CM_NODE_ID" \
  '{mapId:$map,rootIds:[$node]}' > "$CM_CASE/branch-query.json"
cm read branch.get --input "$CM_CASE/branch-query.json" > "$CM_CASE/local-run-branch.json"
CM_RUN_ID="$(uuid)"
jq -n --arg map "$CM_MAP_ID" --arg node "$CM_NODE_ID" --arg run "$CM_RUN_ID" \
  --slurpfile branch "$CM_CASE/local-run-branch.json" --slurpfile plan "$CM_CASE/run-plan.json" '{
    mapId:$map,id:$run,
    branch:{rootIds:$branch[0].data.scope.rootIds,expectedVersion:$branch[0].data.version},
    scope:{nodeIds:[$node]},plan:$plan[0],regenerate:false,mode:"human-in-loop"
  }' > "$CM_CASE/local-run-start.json"
cm_submit uc07-local-start run.start "$CM_CASE/local-run-start.json" > "$CM_CASE/run-started.json"
jq -n --arg map "$CM_MAP_ID" --arg run "$CM_RUN_ID" '{mapId:$map,runId:$run}' > "$CM_CASE/run-query.json"
```

本地 Run 不返回控制租约。直接按 UC-09 查询、UC-10 控制、UC-11 审核即可；没有需要维持的客户端心跳。

### 协作模式：领取编辑权并启动

```bash
jq -n --arg map "$CM_MAP_ID" --arg node "$CM_NODE_ID" --arg holder "$CM_HOLDER_ID" \
  '{mapId:$map,rootIds:[$node],holderId:$holder}' > "$CM_CASE/edit-claim.json"
cm_submit uc07-claim branch.claim "$CM_CASE/edit-claim.json" > "$CM_CASE/run-claim-result.json"
jq -e '.data.status == "claimed"' "$CM_CASE/run-claim-result.json"
# 未 claimed 就停止本用例。
CM_RUN_ID="$(uuid)"
jq -n --arg map "$CM_MAP_ID" --arg node "$CM_NODE_ID" --arg run "$CM_RUN_ID" \
  --slurpfile result "$CM_CASE/run-claim-result.json" --slurpfile plan "$CM_CASE/run-plan.json" '
  $result[0].data.grant as $g | {
    mapId:$map,id:$run,
    branch:{rootIds:$g.branch.scope.rootIds,expectedVersion:$g.branch.version},
    lease:($g|{leaseId,holderId,fence}),scope:{nodeIds:[$node]},
    plan:$plan[0],regenerate:false,mode:"human-in-loop"
  }' > "$CM_CASE/run-start.json"
cm_submit uc07-start run.start "$CM_CASE/run-start.json" > "$CM_CASE/run-started.json"
jq -n --arg map "$CM_MAP_ID" --arg run "$CM_RUN_ID" '{mapId:$map,runId:$run}' > "$CM_CASE/run-query.json"
jq '.data.runControl // null' "$CM_CASE/run-started.json" > "$CM_CASE/run-control.json"
```

**协作模式结果**：编辑租约被消费，范围转为持久 Run 占有；原编辑 lease 不再可用。启动者取得独立控制租约 `runControl`，应按 UC-10 续租。后台 Run 不依赖此控制租约存活。因结果复用而立即终态的 Run 可能没有 `runControl`。

`mode:"auto"` 自动推进；`human-in-loop` 在计划或所定义的结果审核点等待 UC-11。`regenerate:false` 允许复用满足冻结规格与输入条件的历史成果；需要重新生成时用新 Run ID 并设为 true。

多步骤 plan 可以通过 `source:{kind:"step",stepId:"前序步骤",port:"输出端口"}` 绑定前序正式产物，同时在 `dependsOn` 中声明依赖。所有直接 `scope` 输入/上下文必须列入 `scope.nodeIds`，该集合还须位于 branch proof 范围内。不要沿用旧的 `until` 或运行级 `expectedRevision` 参数。

## UC-08 在同图运行多个不相交分支

**参与者 / 前提**：图中存在实际闭包不相交的根 A、B。本地可直接分别启动；协作模式的两个客户端应使用不同的 `CM_HOLDER_ID`。

**步骤**：按 UC-07 的对应模式，分别提交 A、B 的根集合、branch proof、Run ID 和 plan；协作模式另外附编辑 lease。需要两个独立 Run 时执行两次 `run.start`；一次提交两个输入通常创建的是一个 Run 中的多个 Operation。

```bash
cm read map.get --input "$CM_CASE/map-query.json" > "$CM_CASE/map.json"
jq '.data.runs[] | {id,scope,status,paused}' "$CM_CASE/map.json"
```

**结果**：两个 Run 保留在同一快照的 `runs[]` 中，Work 各自携带 runId。暂停、取消、审核都指定目标 runId。一个 Run 暂停不会让另一 Run 的 Work 失效。

**异常**：不同根若共享后继，本地在启动时返回 `BRANCH_BUSY`，协作在领取时返回 busy。不同 branch version 可独立提交，但存储内部继续使用整图 CAS；遇到持续竞争可能返回 `WRITE_CONTENTION`，按原请求重试。不要使用 `runs[0]` 推断“我的 Run”，应按 ID 查找。

## UC-09 查询运行并订阅实时进度

**参与者 / 前提**：Viewer 及以上；已知图 ID 或 Run ID。

```bash
cm read run.get --input "$CM_CASE/run-query.json" > "$CM_CASE/run.json"
jq '.data | {id,status,paused,steps,operations,error}' "$CM_CASE/run.json"

# 此命令持续运行；在另一个终端执行时需重新设置 cm 函数与连接变量。
cm watch "$CM_MAP_ID"
```

**结果**：`watch` 输出逐行 JSON（NDJSON），包括初始完整 snapshot、后续 snapshot、activity、refresh 或结构化 error。snapshot 含 `runs/ownerships/runControls`；`ownershipRevision` 可能上升而内容 `revision` 不变，不能仅用内容 revision 丢弃事件。新连接重新取得完整基线。

Run 状态包括 `running/waiting/completed/failed/cancelled`，`paused` 是独立字段。终态 Run 可能在后续新运行启动时移入历史，仍可用 `run.get` 按 ID 查询。

Ctrl+C 结束 watch，不暂停或取消 Run。watch 不会续租、不代为审批，也不输出完整模型对话。订阅断开后调用方需要重新连接。

## UC-10 暂停、继续或取消运行

**参与者 / 前提**：Editor/Owner；目标 Run 仍为 running/waiting。按模式准备参数，后面的 pause/resume/cancel 命令相同。

### 本地模式：直接指定目标 Run

```bash
jq -n --arg map "$CM_MAP_ID" --arg run "$CM_RUN_ID" \
  '{mapId:$map,runId:$run}' > "$CM_CASE/control-params.json"
```

本地不领取、续租或释放控制权。可以随时暂停、继续、取消，也可在等待审核后直接批准；无需保留终端心跳。

### 协作模式：取得有效控制权

启动时取得的 `run-control.json` 可直接转换为 control 参数；其他客户端或失租后的接管者走下列领取流程。

```bash
jq -n --arg map "$CM_MAP_ID" --arg run "$CM_RUN_ID" --arg holder "$CM_HOLDER_ID" \
  '{mapId:$map,runId:$run,holderId:$holder}' > "$CM_CASE/control-claim.json"
cm_submit uc10-claim run.control.claim "$CM_CASE/control-claim.json" > "$CM_CASE/control-claimed.json"
jq -e '.data.status == "claimed"' "$CM_CASE/control-claimed.json"
# busy 时停止，.data.control 给出当前占用状态。
jq '.data.grant' "$CM_CASE/control-claimed.json" > "$CM_CASE/run-control.json"
jq --arg map "$CM_MAP_ID" '{mapId:$map,runId,control:{leaseId,holderId,fence}}' \
  "$CM_CASE/run-control.json" > "$CM_CASE/control-params.json"
```

### 执行动作

每个动作独立执行；协作模式须在控制租约有效期间操作。本地没有这一期限。

```bash
cm_submit uc10-pause run.pause "$CM_CASE/control-params.json"
cm_submit uc10-resume run.resume "$CM_CASE/control-params.json"
```

```bash
# 仅协作模式：一次新的续租；本地不要执行此命令。
cm_submit "uc10-renew-$(uuid)" run.control.renew "$CM_CASE/control-params.json" > "$CM_CASE/control-renewed.json"
jq '.data' "$CM_CASE/control-renewed.json" > "$CM_CASE/run-control.json"
```

```bash
# 需要取消这个 Run 时执行。
cm_submit uc10-cancel run.cancel "$CM_CASE/control-params.json"
```

```bash
# 仅协作模式：交还控制权但让 Run 继续执行；本地或终态之后不执行此步。
cm_submit uc10-release run.control.release "$CM_CASE/control-params.json"
```

**结果 / 异常**：暂停保留成果和范围占有，撤销该 Run 的 Work 租约；继续后未完成 Work 使用新授权执行。取消保留已发布数据并释放范围及控制租约。控制权释放或到期本身不会取消 Run，其他 Editor/Owner 可以重新领取。

协作 CLI 无内建自动续租。协作模式长期控制应由调用方按约 `leaseMs/3` 调用 renew；等待审核也要续租。网络延迟或挂起时不能假定仍有控制权，服务器以存储时间为准。续租失败后停止控制/审核，保留本地意图，重新读取并领取；禁止自动改用新 fence 重发旧业务请求。本地模式完全跳过这些步骤。

## UC-11 审核计划或候选结果

**参与者 / 前提**：Editor/Owner；目标 Operation 有 `review.state:"pending"`。按 UC-10 准备对应模式的 `control-params.json`：本地只含 mapId/runId，协作额外含有效 control proof。

```bash
cm read run.get --input "$CM_CASE/run-query.json" > "$CM_CASE/run.json"
jq '.data.operations[] | select(.review.state=="pending") | {id,review,stages}' "$CM_CASE/run.json"
```

查看完整候选和计划后，选择实际 Operation ID。下面的 approve 表示当前操作者已经决定批准；拒绝时改为 reject。

```bash
CM_OPERATION_ID='替换为待审核Operation的ID'
CM_DECISION='approve'
jq -e --arg map "$CM_MAP_ID" --arg operation "$CM_OPERATION_ID" --arg decision "$CM_DECISION" \
  --slurpfile control "$CM_CASE/control-params.json" '
  .data as $run | $run.operations[] |
  select(.id==$operation and .review.state=="pending") | {
    mapId:$map,runId:$run.id,operationId:.id,reviewId:.review.id,
    expectedReviewRevision:.review.revision,decision:$decision
  } + (if $control[0].control then {control:$control[0].control} else {} end)
  ' "$CM_CASE/run.json" > "$CM_CASE/review-answer.json"
cm_submit "uc11-answer-$(uuid)" review.answer "$CM_CASE/review-answer.json"
```

**结果 / 异常**：`review.kind` 为 plan 或 result。批准计划可让后续 Agent Work 开始；批准结果可发布候选并推进 Run。运行暂停时可以保存审核决定，后续执行仍需 resume。审核若已经变化，服务器返回 `REVIEW_CONFLICT`；应重新阅读当前候选，不只更新版本号重发。

下一个审核是新的请求。帮助清单中的 `review.update` 是残留项，当前服务端未实现；使用 `review.answer`，它只接受 approve/reject，不编辑模型候选正文。

## UC-12 上传、下载资产并创建来源节点

**参与者 / 前提**：上传需要 Editor/Owner；下载需要 Viewer 及以上。当前模型读取文本来源限 1 MiB，允许 `text/plain`、`text/markdown`、`text/html`、`application/json`。一般资产上传上限 64 MiB，不代表模型能读取全部媒体类型或同等大小。

```bash
printf '%s\n' '用于来源解析的文本内容。' > "$CM_CASE/source.txt"
uuid > "$CM_CASE/source-upload.request-id"
cm upload --workspace "$CM_WORKSPACE_ID" --file "$CM_CASE/source.txt" \
  --media-type text/plain --request-id "$(cat "$CM_CASE/source-upload.request-id")" \
  > "$CM_CASE/source-uploaded.json"
CM_ASSET_ID="$(jq -er '.data.id' "$CM_CASE/source-uploaded.json")"
cm download asset "$CM_ASSET_ID" --output "$CM_CASE/source-copy.txt"
```

上传不会自动创建节点或启动解析。注册目录包含 `factcheck.source@1` 时，创建引用该资产的独立来源根：

```bash
CM_SOURCE_ID="$(uuid)"
jq -n --arg map "$CM_MAP_ID" --arg node "$CM_SOURCE_ID" --arg asset "$CM_ASSET_ID" '{
  mapId:$map,branch:{rootIds:[$node],expectedVersion:null},
  changes:{nodes:{put:[{id:$node,typeId:"factcheck.source",typeVersion:1,
    payload:{locator:{kind:"asset",assetId:$asset,mediaType:"text/plain"},label:"CLI 文本来源"}}]}}
}' > "$CM_CASE/source-node.json"
cm_submit uc12-source graph.apply "$CM_CASE/source-node.json"
```

解析时按 UC-07 的对应模式提交来源分支，选择 `factcheck.parse-source@1`，输入端口为 source，context 为空数组，scope 包含 `CM_SOURCE_ID`。URL 来源使用 `locator:{kind:"url",url:"https://实际公开地址"}`；当前读取不跟随重定向，并限制公开 HTTP(S) 地址。

**其他动作 / 异常**：`asset.list {workspaceId,cursor?,limit?}` 列表；`asset.get {assetId}` 取元数据。Owner 用 `asset.delete {assetId,expectedSha256}` 删除资产，摘要取最新元数据。仍被正式图数据引用时返回 `ASSET_IN_USE`。下载拒绝覆盖已有路径；重试应确认文件状况并选择新输出路径。


选实际 Agent ID，准备新的提示词文件；保留该 Agent 所需的工具调用要求和模板变量。

```bash
CM_AGENT_ID='替换为Agent的ID'
```

## UC-17 处理不确定结果、冲突和失租

**参与者 / 前提**：所有调用者。CLI 失败输出到 stderr，内容为 `ok:false,error:{code,message,errorId,...}`；请保存 errorId 以便定位服务端日志。

**结果不确定时**：网络超时并不证明服务器未提交。重发相同 method、request-id 和参数。使用本文 cm_submit 的操作，直接重发保存的文件即可，例如：

```bash
cm dispatch graph.apply \
  --request-id "$(cat "$CM_CASE/uc05-save.request-id")" \
  --input "$CM_CASE/uc05-save.params.json"
```

成功重放可能返回 `replayed:true` 和当前快照。不要把“新生成 request-id，再创建一次 Run”当成重试。修改 payload、branch proof、lease/control proof 或目标版本后都属于新请求，需要新的操作名和 request-id。

| 情况 | 下一步 |
|---|---|
| `CLIENT_LEASES_DISABLED` | 当前为本地模式，省略 lease/control，按本地 UC 直接提交 |
| claim 返回 `status:"busy"` | 协作模式保持只读，等待释放/到期；新领取尝试使用新请求 ID |
| 本地写入/启动返回 `BRANCH_BUSY` | 有 Run 正在使用重叠范围，等待终态或先处理该 Run |
| `BRANCH_VERSION_CONFLICT` | 保留草稿，读取 branch.get 与图内容，合并后以新请求提交 |
| `BRANCH_LEASE_LOST` / `RUN_CONTROL_LEASE_LOST` | 停止相关写入，重新读取并显式领取；旧 fence 不再使用 |
| `BRANCH_SCOPE_CONFLICT` / `BRANCH_LEASE_SCOPE_CONFLICT` | 用覆盖实际影响的完整根集合重新领取，重新生成 proof |
| `REVIEW_CONFLICT` | 重新读取目标 Run/Operation 的待审版本并重新决定 |
| `REVISION_CONFLICT` | 读取对应工作区、配置或资源版本；检查意图后构造新请求 |
| `WRITE_CONTENTION` / 临时网络故障 | 有限退避，保留原请求身份重试 |
| `IDEMPOTENCY_CONFLICT` | 同 ID 被用于不同输入；核对保存的原请求，不能继续改正文重试 |
| `INPUT_STALE` / `RUN_OWNERSHIP_LOST` | 检查执行输入和持久占有；不要改 Work 或控制 fence 强行继续 |
| 401 / 403 | 检查用户 Token 与资源角色；刷新权限不会恢复旧租约 |

领取/续租成功响应的重放可能是旧收据，不表示租期重新起算；核对 expiresAt 和当前占有。`ownershipRevision` 用于占有快照排序，不是替代 branch version 的内容版本。

**退出码与边界**：0 成功（含 busy 这种业务结果）、2 CLI 用法错误、1 请求/文件等失败、130 已处理的客户端中断。CLI 读取输入文件/stdin 上限 64 MiB，但普通 HTTP JSON 请求体仍限 1 MiB；大文件走 upload。服务端图文档上限为 8 MiB，CLI 响应读取上限 16 MiB。

## UC-18 删除图或工作区

**参与者 / 前提**：删除图需 Editor/Owner，删除工作区需 Owner。先逐一处理该范围内活跃 Run；协作模式还需处理客户端租约。删除命令不会替你取消 Run。以下分别是两个独立操作。

```bash
cm read map.get --input "$CM_CASE/map-query.json" > "$CM_CASE/map.json"
jq '.data | {mapId,expectedRevision:.revision}' "$CM_CASE/map.json" > "$CM_CASE/map-delete.json"
cm_submit uc18-map-delete map.delete "$CM_CASE/map-delete.json"
```

```bash
cm read workspace.get --input "$CM_CASE/workspace-query.json" > "$CM_CASE/workspace.json"
jq '.data | {workspaceId:.id,expectedRevision:.revision}' "$CM_CASE/workspace.json" > "$CM_CASE/workspace-delete.json"
cm_submit uc18-workspace-delete workspace.delete "$CM_CASE/workspace-delete.json"
```

**结果 / 异常**：使用资源版本和删除标记保护重复操作；有活跃 Run 或有效占有时拒绝。分支编辑租约不赋予绕过整图删除条件的能力。物理清理与备份管理属于维护流程。

## UC-19 启动服务、Host 或执行显式迁移

**参与者 / 前提**：本机操作者或部署管理员。以下入口不属于 headless 的 read/dispatch；应在独立终端中运行。

**独立本机**：

```bash
npm run local:serve -- --directory .chongming-local --port 4320 --concurrency 4
```

启动一个 SQLite/API/Host 进程，默认配置容量可调整，不需要 Mongo/RabbitMQ。读取启动输出中的 connectionPath/tokenPath；默认目录中的 connection.json 含 baseUrl、tokenFile、workspaceId。将这些值填入 UC-01。该服务停止会停止本机执行，headless 客户端退出则不影响服务。不要为本机模式另起协作 Host。

**协作部署**：Mongo 副本集、RabbitMQ 和凭据按 [README](../README.md#多host协作) 准备。Graph API 与 Host 使用相同队列部署配置，Host 用内部 Token。

```bash
npm run graph:serve
```

另一个终端：

```bash
npm run host:serve -- --host-id host-a --data-api http://127.0.0.1:4320 \
  --dsh-home /absolute/path/to/host-a --concurrency 4
```

**显式迁移**：旧固定数据模型或单 `run` 文档需要转换；正常启动不会自动迁移。先停止相应服务/Host 并按迁移报告处理有效租约。以下为只读预览：

```bash
npm run admin -- data.migrate-branches --input /absolute/path/to/dry-run.json
# dry-run.json 内容为 {}

npm run local:serve -- --directory .chongming-local --migrate-branches
```

正式应用时 Mongo 输入文件使用 `{"apply":true}`；本机入口加 `--apply`。二者各自作用于配置中的存储，请勿对正在使用的数据目录启动第二个 SQLite 服务。

管理员入口还包括 init、user.create、token.create/revoke、user.disable/enable、agents.seed、settings.read、secret.set、database.test/stage、endpoint.test 和资产维护。具体部署与输入参数见 [README](../README.md)、[本机运行说明](./065-本机运行说明.md) 与 [管理入口源码](../apps/graph-server/admin.ts)。
