## 1. 本次修订的设计依据

唯一采用的设计 skill 是 [codebase-design](/Users/xiong/.codex/skills/codebase-design/SKILL.md)，以及它的 [DEEPENING.md](/Users/xiong/.codex/skills/codebase-design/DEEPENING.md) 和 [DESIGN-IT-TWICE.md](/Users/xiong/.codex/skills/codebase-design/DESIGN-IT-TWICE.md)。不叠加其他设计 skill。

目标：让调用方通过简单的 interface 完成完整业务，把正确性规则和修改集中在相应 module 内。可读性改善既包括 implementation 内部的清楚表达，也包括调用方无需反复理解鉴权、重放、版本和取消的顺序。

用户要求的中文用途注释、消息枚举、节点级恢复、树状图和本机/协作部署均继续保留。skill 中“返回结果”的原则用于避免纯计算暗改输入，不代表取消必要数据库写入；“替换旧测试”必须以对应行为已有新验证为前提。

沿用现有TypeScript、Vue、Node HTTP和DSH，依赖由apps显式装配；本计划不引入NestJS、装饰器、反射容器、通用CommandBus或生命周期基类。

## 2. 术语和当前事实

### 2.1 设计词汇

| 术语 | 本计划含义 |
|---|---|
| module | 有 interface 和 implementation 的一组完整能力；可以是函数、类或多个文件 |
| interface | 调用方必须知道的全部规则：参数、返回值、顺序、权限、错误、并发和资源生命周期 |
| implementation | module 内完成这些能力的代码；内部可以有多个小函数和文件 |
| seam | 可以替换行为的位置；存储、执行器、传输等差异在此接入 |
| adapter | 满足 seam 上 interface 的具体实现 |
| depth | 调用方学会少量规则后能完成多少完整行为，不按实现行数衡量 |
| locality | 一项规则的变更、排错和验证能否集中在同一处 |

业务词继续用 Map（数据图）、Run（一次运行）、Operation（某节点的一次处理）、Work（可领取工作）、Review（审核）、Lease（租约）、Receipt（收据）。仓库目前没有独立 CONTEXT.md，本计划暂承载这些已有词义，不另造同义名。

## 4. 先确认 seam 是否真实存在

依据 DEEPENING 的四类依赖逐项选择验证方式：

| 依赖 | 类别 | 实际 seam / adapter | 验证方式 |
|---|---|---|---|
| 节点闭包、审核、提案选择、纯校验 | in-process | 同一个 module 的 implementation；无需额外 port | 通过 module 的可观察结果断言，必要内部算法测试保留 |
| 临时目录、配置文件、本机进程 | local-substitutable | 临时目录、真实测试子进程；通常属于 implementation 内部 seam | 文件/进程集成测试，不为每次 readFile 新建 interface |
| 图持久化与事务 | 本地可运行依赖，且有两种生产 adapter | 已有 Persistence/GraphStore：SQLite、MongoDB | 两种真实 adapter 都测试；SQLite不能代替Mongo证明事务和接管语义 |
| UI/Host 访问自有 Graph API | remote but owned | 已有客户端/工作协议；HTTP 与测试用受控 adapter | interface行为测试，加真实HTTP合同测试 |
| Work 传递与变更通知 | 自有部署通道 | 进程内通知、RabbitMQ是实际不同adapter | 两者行为回归；ACK/重投/断连必须保留真实RabbitMQ测试 |
| 模型、DSH SDK、外部资料访问 | true external | 已有 runner/来源读取 seam；真实adapter和确定性测试adapter | 主流程使用受控fixture，另外保留DSH/来源协议集成检查 |

优先复用现有 seam。新 port 必须写出至少两种确有用途的 adapter（可以是生产与测试）；不能为一个仅包装常量的测试替身制造理由。装配内部的替换点不因为测试需要就公开给所有调用方。

公开 interface 接收完成业务所需的信息；其内部存储与传输依赖由 apps 显式装配。依赖注入不等于让每个业务调用都传事务、存储对象和配置。

## 5. 图命令 interface：三种方案比较与决定

本节依照 DESIGN-IT-TWICE 对同一候选分别设计；以下是 interface 形状示例，不是新增网络协议。

### A：沿用命令 interface

调用形式：
~~~ts
application.dispatch(token, {
  requestId,
  method: 'run.pause',
  params: { mapId, runId, expectedRevision },
})
~~~

调用方提供令牌、命令身份和参数；module 拥有鉴权事务、Receipt、版本检查、配置解析和提交顺序。查询继续使用 read。现有 GraphSuccess 包装仍由 HTTP adapter 按现行方式输出。

收益：当前调用方无需学习另一套命令表示；规则可以在 implementation 内重新组织，外部行为测试稳定。代价：内部若仍是一长串无名称的分支，阅读体验没有改善，必须以具名用例函数说明步骤。

### B：显式用例方法

调用形式：
~~~ts
graphCommands.pauseRun(token, {
  requestId,
  params: { mapId, runId, expectedRevision },
})
~~~

每个方法封装完整写入；共用鉴权事务实现保持私有，不暴露 transaction(callback) 让调用方自己拼装。

收益：常用动作、参数和导航位置直接。代价：HTTP命令到方法多一份映射；新增业务动作需同时维护外部method与内部方法；目前多数调用方本来就持有命令对象。

### C：绑定某张 Map 的操作对象

调用形式：
~~~ts
const map = graphs.forMap({ token, mapId })
await map.pause({ requestId, runId, expectedRevision })
~~~

对象只绑定原始token/mapId；不能缓存已授权身份、workspace角色、revision或事务。每次调用仍重新进行短事务内鉴权。

收益：连续操作同一张图时减少重复参数。代价：对象容易被误解为已授权会话或跨动作事务，单请求通常只用一次；图创建和跨图动作又需另一组interface。

### 决定

选择 A。B 的具名用例组织方式用于 A 的 implementation，避免同时公开两套同义入口。C 暂不采用。

这是保留已经有价值的 interface，不把“保留read/dispatch”本身记成新增depth。实际验收对象是：移除业务调用方对原始 store/未鉴权 graph.dispatch 的依赖，减少必须手动排序的规则，并使相关变更集中维护。

管理初始化、资产流、Work协议和生命周期有不同调用者与约束，不为了凑两个方法把它们全塞进一个任意命令总线。apps 可以持有完整装配结果，但每个调用者只接收它需要的 interface；安全仍由运行时鉴权保证，不由TypeScript的可见字段保证。

## 6. 候选 module 及其价值

下表定义能力，未承诺一行对应一个新类或新文件。一个module可以包含现有几个文件；候选若只是转发则不新增。

| 候选 | interface 应表达什么 | implementation 内集中什么 | 删除测试：去掉后会怎样 |
|---|---|---|---|
| 公开图命令 | read/dispatch；每次重新鉴权；新命令或合法重放的结果 | user/workspace fence、Receipt/hash、revision、配置和资产引用检查、提交 | 若调用方重新要拼鉴权/判重/提交，则module有价值；纯外包一层则无价值 |
| Work状态 | 领取/读数据/续租/释放/提交；明确busy/obsolete/accepted与错误 | 工作身份、历史提案重放、有效租约、节点推进及CAS | 若Host要重建图并判断是否还可执行，说明应保留该module |
| 授权图观察 | 建立/取消观察；输出基线、变化、活动、访问终止 | 首次订阅与读取顺序、发送前权限校验、合并变化、关闭 | 若各输出adapter都要复制“读取后再鉴权”，说明存在真实集中价值 |
| 客户端会话 | 连接、选工作区/图、提交、重试、释放；只读视图 | 代次、旧响应隔离、快照与活动更新、偏好合并、原请求重试 | 若Vue组件重新要协调timer/epoch/AbortController，说明应保留module |
| Host执行 | start/close/finished；消费结果与关闭期限 | 每次Work的runner、续租、活动、取消、等待清理和重试分类 | 若队列调用方要手动安排续租和资源排空，说明执行module有价值 |
| 桌面本机运行 | 启动后给连接、读取状态、关闭 | 合并启动、IPC就绪、父子进程、关闭期限与必要终止 | 若Main每次都要管理子进程细节，说明应保留module |

每次建立或拆分 module，先写一张卡：调用者、现有知识负担、interface完整规则、隐藏的implementation、依赖类别/adapter、删除测试、可观察测试。无法说明新增价值时，只整理已有implementation，不添加文件外壳。

### 6.1 事务和副作用

公开图命令内部顺序：进入事务 → 在其中验证token/user并写fence → 取得本次工作区写权限并写fence → 核对Receipt → 合法重放直接返回 → 新请求检查版本/用例条件 → 更新图状态 → 原子提交。

图创建、删除及资产导入等现有特例保留独立步骤。重放保持现行的当前快照及原Receipt产物字段，不改成返回历史瞬时快照。

auth.transact、requireRole、controlReadCopyLibrary和controlValidateTools的写入职责必须从命名和中文说明可见；内部可以使用“获取写授权/锁定库版本”等明确步骤，外部调用者不负责按顺序调用这些步骤。

工作区Agent写入和跨资源复制由同一上层module组织事务；库/设置规则接收明确数据与事务，不反向调用工作区module。避免因拆catalog产生循环依赖。

### 6.2 客户端状态

一个对Vue的会话interface可以拥有内部状态分组，先定义所有者，再决定是否值得提取为独立内部module：

| 状态 | 单一所有者及对外结果 |
|---|---|
| 身份、连接、会话代次 | 会话本身；其他内部逻辑只能消费当前作用域 |
| 工作区、标签、选中节点 | 工作区状态；导出只读视图和偏好快照 |
| 当前图、临时activity、视图代次 | 图观察状态；统一接受或丢弃成功/错误回调 |
| 偏好dirty/blocked及保存队列 | 内部偏好写入器；完成旧保存不清新工作区dirty |
| 冻结payload/requestId及重试 | 内部命令提交器；一次未确认操作只有一份重试身份 |

不预先要求 ClientSession/WorkspaceSession/MapSubscription/PreferenceWriter/CommandSubmission 五个公开对象。不把全部refs传给每个对象，也不通过环形回调继续共享写权限。

HTTP请求拥有自己的取消和期限；SSE传输拥有reader、分帧和首帧/空闲期限；会话拥有唯一重连。scope、epoch和版本比较不泄漏给Vue组件。computed留在Vue adapter中，保持树布局和视口行为。

### 6.3 生命周期

HostWorker、LocalServiceProcess这些名字描述能力，不强制用class。选class时构造只保存依赖、传出方法显式绑定this；选函数时把每个可变资源限制在所属生命周期。

每次Work独享grant、execution/renewal信号和deadline；Host停止、消息投递断连、租约丢失分别有明确语义。close先停止新工作，再中止并等待DSH清理、执行有界释放、关闭连接。关闭期限和幂等性属于interface。

Host错误矩阵区分连接失败、429/5xx、LEASE_LOST、领取401/403、非法协议和模型失败；不靠message.includes分类，也不因共享HTTP代码统一重试所有错误。

私有interface用于内部测试可以存在；不因为要测一个函数就把它变为所有业务调用者可用的公共能力。

## 8. 注释、命名和枚举随切片完成

### 中文用途注释

保留用户对每个函数的要求，覆盖维护源码、Vue script、具名箭头、对象方法、构造、匿名回调、测试辅助函数和工程配置；第三方、生成文件及历史快照明确排除。

有块状函数体时注释放在签名下、函数体第一行。表达式箭头可用紧邻函数表达式的块注释，不为注释改变返回语义；无函数体的接口签名在前一行说明。

逐函数读实现与调用者，说明具体对象、动作、必要副作用。例：“把短时间内的标签页和节点选择变化合并，稍后一起保存”“验证本次写入权限，并与并发撤权操作保持事务冲突”。比较/筛选回调也写对应具体用途，不写“处理相关工作”。

AST只负责完整盘点，人工确认是否准确、人话、无重复；格式检查按真实语法结构，不能用错误生成器的同一算法自证。旧的071模板逐切片重写，最后对未触及位置扫尾。

### 命名和排版

同一业务概念使用一致名称；名称体现写库、取消、启动等副作用。必要的内部方法可以简短，不为满足模块前缀堆长名。修改规范时同步coding.md并清理退役机制示例。

一行一项状态变更，复杂条件分行，分支用名字表达。不设置类/方法的硬行数限制。拆掉一个函数后若调用者需要新增排序知识，就要重新评估。

### 错误枚举

保留字符串枚举。先按引用盘点实际含义；同一个切片的消息一起完成语义命名和引用迁移。跨module共享内容放contracts，私有文案跟随implementation；文件划分服从使用关系，不为480个成员平均分组。

保留原输出文字与error字段；相似文字未经行为核对不合并。动态模板用有含义的参数或少量明确格式化函数，缺参不能生成undefined。DSH及原生Node脚本使用能直接加载的冻结枚举，不增加生成框架。

P0登记所有已知漏点，处理其所属切片时修复；最终统一检查streamError赋值、Vue校验/错误呈现、脚本错误和命名别名。合法空串清状态、普通按钮、提示词及远端动态错误分别定义，不把所有字符串当错误。

检查器正反例必须覆盖实际漏点，同时确认合法调用通过；报告准确扫描范围，不宣称有限AST规则证明全库语义。

## 9. 执行顺序：先验证一条完整路径

| 阶段 | 工作 | 退出证据 |
|---|---|---|
| P0 真实基线 | 保存工作区与未跟踪文件，列调用者/状态/消息/注释清单、adapter和行为矩阵 | 原有失败有记录；快照可恢复；未把tests未类型检查当作通过 |
| P1 暂停/恢复切片 | 沿现有dispatch走通鉴权、收据、版本、状态、旧grant隔离；整理名称/用途和implementation | 同一interface在两种存储验证；调用者不认识事务/fence细节；无新增转发外壳 |
| P2 图命令与Work | 按同样方式覆盖运行、审核、编辑、提案和历史重放，梳理各自调用面 | 完整命令与Work协议测试；各新闻/事实/方向继续独立领取 |
| P3 Host与桌面 | 集中资源所有权、错误矩阵、续租/关闭；样板工作从领取到清理完整迁移 | 断连、接管、关闭期限、启动合并和凭据隔离通过 |
| P4 客户端会话 | 先切图与订阅，再扩展连接、偏好、提交重试；Vue只消费会话interface | 迟到成功/失败隔离、唯一重连、原请求重试、旧偏好竞争通过 |
| P5 其余module | 配置复制、成员、资产、授权观察和HTTP adapter按真实理解负担逐项整理 | 同一事务、无循环依赖、流读取及SSE基线/访问语义保持 |

| P7 总体验收 | 双部署、树状界面、故障路径、打包运行时、文档和可读性复核 | 每个不变式有行为证据；必要旧测试完整保留或有明确替代 |

P1不以增加module为硬目标。若现有公开interface已足够深，成果可以是内部规则明确、权限外露减少、修改集中和错误说明准确，不能虚构“调用次数减少”。

所有阶段同时处理触及函数的中文说明、命名、类型和消息；不用先完成全库格式/枚举工程才能验证样板。内部导入或名称切换一次改完调用方，不留并行实现；外部协议不迁移。

## 11. 接受、停止和回退标准

每个结构变更必须给出以下对照：

1. interface：调用者以前/现在需要知道哪些规则？哪些细节已由module保证？
2. locality：修改同一条规则，需要同步改动的独立位置是否减少？模块内小文件数量不代替这个指标。
3. 删除测试：去掉新增module，复杂度是否回到多个调用者？若只是少一个跳转，应撤销外壳。
4. 依赖：新增seam是否有实际adapter？替换点是否应保持内部？
5. 行为：本切片涉及哪些I编号，有什么通过证据？
6. 人工阅读：注释是否说出用途和副作用，主流程是否还要求脑内追踪共享状态？

没有depth/locality收益的结构改动停止，不以完成预设目录图为目标。新增功能缺陷先登记复现，再作独立修复块，不夹在文件搬迁中改变行为。

每阶段保留可运行状态，用精确文件快照和差异回退；不重置用户脏工作区。原有共享协议与schema保持，因此不需要部署切换和数据回滚。公开图创建、历史提案重放、流上传等特例必须单独复核。

最终交付：实现、真实行为/类型/界面验证记录、ARCHITECTURE.md与coding.md同步、消息与函数盘点范围、已替换测试说明。随机走读运行启动、报告提交、暂停恢复、Agent复制、切图五条路径，能定位interface、规则所有者、失败策略和adapter。
